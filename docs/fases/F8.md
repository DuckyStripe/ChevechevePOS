**Decisiones de este brief**:

- **Ventas en espera en el navegador** (A3): hasta 5 carritos en `localStorage` con llave `chv:pos-espera:<usuario>:<caja>`;
  cada uno con su `clave_idempotencia` (creada al abrir el carrito, no al cobrar) y su cliente. Cobrar uno borra solo ese.
  `shortcut`: se pierden si se borra el navegador o se cambia de equipo; tabla `venta_espera` si hace falta entre equipos.
- **Escáner** = lector USB/Bluetooth en modo teclado (teclea el código + Enter) sobre un campo con foco permanente;
  `GET /presentaciones/codigo/:codigo?lista_precio_id` (F2). En el cascarón Android no hay cámara-escáner en F8 (fuera de
  alcance); el buscador tolerante (`fn_buscar_productos` vía `GET /catalogo-venta` filtrado en el navegador) cubre el resto.
- **Ticket**: componente único `componentes/ticket/ticket-80mm.tsx` que pinta la forma `Ticket` tal cual (montos string,
  sin sumar en JS; sin IVA/IEPS); lo usan `/pos` (al cobrar) y `/ventas/[id]` («Reimprimir»). Encabezado y pie salen de
  configuración (`negocio_nombre`, `negocio_direccion`, `negocio_telefono`, `ticket_pie`); las etiquetas de columnas son
  controles. Sin driver ESC/POS: `window.print()` con la impresora térmica predeterminada (`shortcut`: si corta mal, se
  mide el ancho real y se ajusta el CSS).
- **Corte**: el esperado lo da `fn_resumen_turno` (§2.8); la pantalla solo pide el contado y muestra la diferencia que
  devuelve la API. Corte supervisado = `POST /turnos/:id/cerrar` sobre un turno ajeno con `caja.supervisar` desde
  `/caja?turno=<id>`.
- El pedido «recoge» se entrega en `/cobrar?pedido=` (F7) con el turno de mostrador, nunca en `/pos` (N1).

## Paquete C — API: pruebas de paridad del mostrador (dueño: `apps/api/test/{pos,corte,ticket}.test.ts`, `apps/api/test/ayuda-f8.ts`; correcciones en `modulos/{ventas,turnos,cajas}/**` solo si una prueba demuestra un fallo, avisando al coordinador)

**Juego fijo**: el de F7 (Corona Caja `400.00`, Six `105.00`, Pieza `18.00` en Menudeo y Caja `380.00` en Mayoreo, existencia
240 a `12.500000`); cliente **C** (`limite 1000.00`, `dias_credito 7`, Menudeo); cliente **M** con lista Mayoreo; turno de
mostrador del Dueño con `fondo_inicial 1000.00`.

| Caso | Esperado (código exacto) |
|---|---|
| Sin turno | `POST /ventas` → 409 `TURNO_NO_ABIERTO`; con turno de ruta → 409 `TURNO_NO_VALIDO` |
| Venta con cambio | 1 Six, efectivo `105.00`, recibido `200.00` → 201 `Ticket` con `total "105.00"`, `cambio "95.00"`; misma clave → 200 mismo `folio`; otro cuerpo → 409 `IDEMPOTENCIA_CONFLICTO` |
| Mixta efectivo + crédito | C, 1 Caja: efectivo `250.00` + crédito `150.00` → CxC `150.00` con `vence_el = hoy + 7`; crédito sin cliente → 409 `CREDITO_SIN_CLIENTE`; Σ ≠ total → 409 `PAGOS_NO_CUADRAN` |
| Mayoreo | M, 1 Caja sin precio → `importe "380.00"` (su lista, sin permiso); Cajero manda `lista_precio_id` Menudeo para M → 403 `SIN_PERMISO_PRECIO`; Cajero con `precio_unitario "390.00"` → 403 `SIN_PERMISO_PRECIO`; Dueño → 201 |
| Última caja concurrente | existencia de Victoria = 24 (1 caja); dos conexiones venden 1 Caja a la vez → una 201, la otra 409 `STOCK_INSUFICIENTE`; existencia final 0 |
| No vender lo cargado | ruta cargada con 126 pz de Corona → mostrador 5 Cajas → 409 `STOCK_INSUFICIENTE {disponible:114, comprometido:126}` |
| Corte | en el turno del Dueño: Six efectivo `105.00`, Caja efectivo `400.00`, la mixta (`250.00` efectivo), una Pieza efectivo `18.00` cancelada por el Dueño en el mismo turno (reembolso `18.00`), retiro `500.00`, salida `50.00` «Bolsas» → `efectivo_esperado "1205.00"` (= 1000 + 105 + 400 + 250 + 18 − 18 − 500 − 50); cerrar con `1200.00` → `diferencia "-5.00"`, turno `cerrado`; cerrar otra vez → 409 `TURNO_NO_ABIERTO` |
| Corte supervisado | turno de un Cajero cerrado por el Administrador (`caja.supervisar`) → 200 con `cerrado_por` = Administrador; por otro Cajero → 403 `TURNO_AJENO` |
| Cancelar | Administrador → 403 `SIN_PERMISO {permiso:'ventas.cancelar'}`; Dueño → 200 y la venta sale del corte como venta cancelada (`ventas.canceladas 1`) |
| Ticket | `GET /ventas/:id/ticket` dos veces → mismo JSON (reimprimir = mismo ticket); ninguna llave `iva`/`ieps`/`impuesto` (recorrido recursivo); `saldo_credito` presente solo si hubo crédito; Cajero con la venta de otro → 404 |
| Recoge | pedido `recoge` entregado por `/pedidos/:id/entregar` con el turno de mostrador → venta `origen "pedido"` en ese turno |

Validación C (en su turno): `npm run lint --prefix apps/api && npm run typecheck --prefix apps/api && npm run prueba --prefix apps/api -- test/pos test/corte test/ticket test/ventas test/turnos`.

## Hechos de la implementación (sin commit; **escrita**, pendiente del agente `revisor` y de la prueba manual con lector e impresora; ya en CONTRATOS §4.4 y PLAN)

- Sin migración ni rutas de API nuevas: `/pos` usa `POST /ventas` y `POST /cobrar/vista` (la vista previa calcula total, cambio y
  crédito en SQL; la web no suma), `GET /catalogo-venta`, `GET /presentaciones/codigo/:codigo`, `GET /clientes?buscar`,
  `GET /clientes/:id` y `GET /turnos/actual`. Sin turno de **mostrador** abierto no se vende (un turno de ruta tampoco vale):
  la pantalla manda a `/caja?volver=/pos`.
- **Ventas en espera**: en el navegador (`localStorage`, llave `chv:pos-espera:<usuario>:<caja>`); cada una nace con su
  `clave_idempotencia` al abrirla y la conserva al reintentar.
- Ticket 80 mm (`componentes/ticket`): `GET /ventas/:id/ticket`, sin desglose de impuestos; «Reimprimir ticket» en `/ventas/[id]`
  (solo ventas `completada`). `/ventas` y `/ventas/[id]` (cancelar, devolver) son de F7.
- `/caja` (F7) gana: corte supervisado `?turno=<id>` con `caja.supervisar` (cierra con el mismo `POST /turnos/:id/cerrar`), lista de
  turnos abiertos para supervisar y «Imprimir corte» (hoja 80 mm del `fn_resumen_turno`).
- Entrada de menú «Vender» (`/pos`, `ventas.crear`, grupo `mostrador`).
- **Paquete C: hecho** (`test/{pos,corte,ticket}.test.ts`, `ayuda-f8.ts`; 10 pruebas de paridad en verde, sin correcciones en `modulos/**`). Notas: `POST /turnos/:id/cerrar` no devuelve `cerrado_por` (la prueba lo verifica en `turno_caja`); `saldo_credito` del ticket es el saldo actual del cliente (CONTRATOS §4.4), `null` sin cliente.
