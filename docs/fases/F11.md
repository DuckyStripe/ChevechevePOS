# F11 — Crecimiento: lealtad simple y «en tu zona también piden» (brief ejecutable)

Para agentes implementadores (`sonnet`: `api-dev` para B y C; `web-dev` para D y P). **Manda `docs/CONTRATOS.md`** (§2.12
B14 y B15, la fila `fn_orden_carga` de §2.7, §2.1.1 plantillas `pantalla_lealtad_*`, §4.4 «Cambios F11», §5 nota de
lealtad, §7.1 C18/C19); este brief solo reparte, ordena y fija los números de prueba. Si algo no cuadra con el contrato: se
reporta, no se decide. Reglas de `CLAUDE.md` vigentes (sin commit/push/ramas/worktrees; `.env*` no se editan; pruebas solo
contra `chevechevepos_pruebas`; archivos temporales con nombre único por agente).

**Sin IA ni APIs de pago**: lealtad y sugerencias son reglas en SQL con pruebas. **Regla del dueño: nada de builds**.
Validación: solo lint, typecheck y pruebas.

**Requisito**: F9 en `main` (009 aplicada). F10 (envases, `010_envases.sql`) está diferida y **no** es requisito.

**Toca dinero, stock y permisos** (una línea regalo a precio 0 saca producto del inventario y baja la utilidad): cierre con el
agente `revisor` (opus) obligatorio.

## Migración 011 con el hueco de 010

`apps/api/scripts/migrar.mjs` toma `^\d{3}_.+\.sql$`, ordena los nombres (`sort()`) y aplica los que no están en
`app.migraciones`. **No exige números seguidos**: `011_crecimiento.sql` se aplica sin `010`. Consecuencia que hay que
respetar: cuando algún día llegue `010_envases.sql`, en una base que ya tiene 011 se aplicará **después** de 011, y en una
base vacía **antes**. Por eso 010 y 011 deben ser **independientes** (ninguna crea, rehace ni lee objetos de la otra). 011
no toca envases; si 010 necesitara rehacer `fn_registrar_venta`, partirá del cuerpo de 011 y lo dirá su brief.

- B va solo y primero: C llama sus funciones. C, D y P escriben en paralelo; D y P trabajan contra §4.4 «Cambios F11».
- **D escribe primero los tipos `// F11`** de `lib/tipos.ts` (lista exacta en D); P solo los importa (un archivo, un dueño).
- **Un solo agente corre `npm run prueba` a la vez** (borra y recrea `chevechevepos_pruebas`). Candado: `mkdir
  /tmp/chevechevepos-prueba.lock` antes de correr (si existe, esperar o avisar al coordinador) y `rmdir` al terminar,

  renombra a `.sql` al tomar el turno de pruebas. **Nunca se editan 000–009** (el migrador falla por checksum).

| **Existencia del regalo** (no puede fallar la venta) | Se agrega solo si cabe: piezas del regalo ≤ `existencia − cargadas − (piezas de esta venta del mismo producto, solo en mostrador y recoge)`. Si no cabe, o la presentación regalo ya no está `activa`/`se_vende`/producto activo: **sin línea regalo, sin canje**, la venta pasa igual y el premio sigue pendiente |
| Reparto: el regalo debe ir en la camioneta | `fn_orden_carga` (misma firma) agrega `regalos` = paradas `entrega` cuyo cliente tiene premio pendiente; quien carga lo sube. No cuenta en `FALTA_SURTIR` ni en `cajas_totales` (aviso, no reserva). Al entregar, si no cabe en la existencia libre, no se da y regresa |
| Cancelar y devolver | Disparadores, sin copiar `fn_cancelar_venta` ni `fn_registrar_devolucion`: cancelar una venta escribe un `reverso` = −Σ de sus movimientos (el premio canjeado vuelve a pendiente; el regalo regresa al inventario con el resto de la venta). Devolver piezas de una línea que acumuló resta `floor(devueltas/factor)` nuevo − anterior. Devolver el regalo no repone el premio. El saldo puede quedar negativo; se muestra `llevas = greatest(0, saldo)` |
| Tipos de movimiento | `acumula`, `canje`, **`reverso`** (B14 solo decía los dos primeros; se agrega `reverso` para no borrar ni editar filas: la tabla es inmutable) |
| Quién configura | Regalar producto es fijar un precio: `PATCH /configuracion` con llaves `lealtad_*` y `PATCH /presentaciones/:id` con `cuenta_lealtad` exigen **además** `precios.editar` (solo Dueño, §5). Sin permisos nuevos |
| Validar la configuración en SQL | `fn_lealtad_configurar` escribe las 3 llaves; prender sin regalo válido → `VALIDACION {campo:'lealtad_presentacion_regalo_id'}`; `lealtad_cada` entero 1–1000 |
| Textos al cliente | La línea C19 sale **renderizada en SQL** de las plantillas `pantalla_lealtad_avance` («Llevas {{llevas}} de {{meta}} cajas para una {{regalo}} gratis») y `pantalla_lealtad_premio` («¡Ya ganaste! Tu siguiente pedido lleva {{regalo}} gratis»), editables en `/configuracion/plantillas`. El título corto «En tu zona también piden» es etiqueta de control (`textos-publico.ts`, C6). Ningún mensaje `wa.me` nuevo |
| Sugerencias: «compró» | Ventas `completada` (devueltas o no; el regalo recibido también cuenta como compra suya) |
| Sugerencias: exclusión por **producto** | No se sugiere ninguna presentación de un producto que él compró en la ventana (compró Six de Modelo → no se sugiere Caja de Modelo). Cumple la regla bajo cualquier lectura |
| Sugerencias: ventana de 60 días | `v.creado_en >= fn_inicio_dia(fn_fecha_local(now()) − 60)` para él y para la zona (hora de México) |
| Sugerencias: zona | La zona **actual** (`cliente.zona_id`) de cada comprador; él sin zona → `[]`. Mínimo 3 clientes distintos de la zona (sin contarlo a él); el regalo de lealtad no cuenta para la zona |
| Sugerencias: una por producto, máx. 3 | Por producto, la presentación con más clientes (empate: mayor `factor`, luego menor `id`); orden final `clientes desc, producto.nombre, presentacion_id`; `limit 3` |
| Sugerencias: precio actual | Solo presentaciones `activa`, `se_vende`, producto activo, categoría activa y `fn_precio(pz, lista del cliente)` no nulo; la respuesta trae **solo** `presentacion_id`: el precio es el del artículo del mismo catálogo (de la base, al momento) |
| Privacidad de la sugerencia | No sale el número de clientes, ni nombres, ni montos: solo el id de un artículo que él ya ve en su catálogo. El mínimo de 3 evita deducir a una tienda concreta |
| Candados | La lealtad **no agrega candados**: su saldo se lee después de `cliente FOR UPDATE` (ya en el orden ruta → turno → pedido → líneas → venta → cliente → existencias → CxC → abono). Cancelar y devolver ya bloquean al cliente antes que existencias, y sus disparadores solo insertan. Dos ventas del mismo cliente se serializan en el cliente: un solo canje |
